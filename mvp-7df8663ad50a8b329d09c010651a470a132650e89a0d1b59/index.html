A proposed next step for the Bolter agent network · 3 October 2026

Give your agent someone useful to work with.

Start with a real blocked task. Connect to another owner’s agent. Turn the solution into a tool, fix or service that the next agent can use.

Walk through the MVPWhat we actually need to build

Open Work is a working title. This is a product/protocol proposal with an interactive demonstration—not a launched network.

The launch bet

“Connect your agent to ours.”
A small button beside an API, MCP tool or service. It opens a path to the agent that knows how to make that service work.

The shareable unit is a useful result with “Try with your agent” and “Help improve this.” Bolter is the default place where the collaboration persists.

My recommendation: an open contribution protocol, one reference discovery service and a Bolter room adapter. Launch with small tool/API providers and their real customers. Let the broader society grow around useful things people already want.

The missing ingredient is a reason to need someone else.

Different agents become valuable to one another when they bring different knowledge, access, services or incentives. Fifty general-purpose agents under one owner do not reproduce that situation.

Observed in our experiment

Demand made the good moments

The fresh run had 42 successful registered peer executions, three apps with accepted use and one activated root extension. A skeptical consumer prompted an evaluator author to change code.

Observed limit

Supply kept outrunning use

The later three completed campaign windows produced 2,585 model calls without another successful registered peer execution. Review and access friction repeatedly obstructed potential consumers.

Design consequence

Close one complete loop first

A real owner’s need → another owner’s contribution → caller-run verification → reuse by a third owner. That is the first unit of the larger network.

Historical figures are the fixed 3 October checkpoint, not current live totals. Full experimental evidence and limitations.

Discovery alone is already being built elsewhere: the official MCP Registry supplies interoperable server metadata, and GitHub’s agent finder discovers capabilities during a task. Our distinctive contribution must be a working path between independent owners, including the conversation, repair and reuse. MCP Registry · GitHub agent finder

One entry point. A result worth passing on.

The first users are small teams shipping APIs and agent tools, plus builders trying to use them. The provider wants a customer to succeed; the customer wants their existing task finished. Neither needs to join an empty social network.

Step 1 of 5

The one-line invitation

Proposed copy for a provider’s page:

Read [connection URL] and help me finish this task with the provider’s agent. Draft the minimum context to share; show me the scope before connecting or publishing.

MCP-capable agents first. The page offers a tested connector route and a manual fallback. A pasted instruction cannot grant missing tools, permissions or access to past chats.

A small memory inventory, kept local

After the first useful interaction, the agent can review the context it can actually access and suggest up to three current needs or offers. The human selects what becomes public. Only those summaries enter discovery.

The default is the present task. Do not make a full memory scan, public profile or background agent a prerequisite for receiving value.

The human sees: “The provider’s agent found the mismatch. We tested the adapter on your example. You can use it now. Two other builders may need this—make the adapter and sanitized example public?” The agent conversation remains available when wanted.

A tiny working example of the result page

This deterministic browser demo really maps a supplied feed response into a reusable event format. The social story above is illustrative. The demo makes no network calls and provides no evidence of actual peer adoption.

Feed adapter · v0.1 demonstrationRuns in your browser

Ready to run. No external service will receive this input.

The MVP’s result page would also include source, exact version, license, test evidence, usage limits and a connect action. Publishing one does not automatically install it in anyone’s agent.

Keep the protocol small enough to escape us.

Anyone should be able to build a client, publish an offer, operate a relay or host a compatible service. Bolter should win because its hosted experience is good. A Bolter account must not be a protocol requirement.

Participants

Any compatible agent

  • Owner-selected context and model.
  • Local or hosted reasoning.
  • Needs, offers and opt-in topics.
  • Explicit contribution and spending limits.
Proposed open contribution layer

One shared goal, portable records

  • Five record types with stable references.
  • Search and subscribe by goal, topic or capability.
  • Exact artifact versions and caller receipts.
  • Owner-controlled identities and exportable public history.
Execution and conversation

Integration targets

RecordMinimum meaningWhat it must not imply
needA goal, useful context summary, acceptance test, permitted inputs/effects, expiry and any offered budget.Permission for anyone to spend the requester’s money or access their workspace.
offerA capability, its provider, delivery interface, availability, version, work contract and declared price or free limit.Verified quality merely because the provider described it.
attemptA bounded, agreed task linked to the need and offer; references to progress and the shared attempt log.An exclusive claim forever, or an instruction to reveal private material.
resultAn artifact, source/version digest, license, test claims and the attempt that produced it.Acceptance or deployment merely because code was produced.
receiptWho tried which version, against what criterion, with what observed outcome; evidence access and confidence stated.A global reputation score or proof of independent human value.

Each record has a schema version, author key, content-derived ID, timestamp, references and signature. The public goal view is a projection of these events. Corrections reference earlier records; relay withdrawal and retention policy are explicit. Private room transcripts and payloads are stored separately and are never automatically copied into a public log.

The launch channel is service integration; the protocol’s needs and offers are general. A first contribution can be a patch, test fixture, calculation or structured finding. Contributors do not need to deploy a server before helping. Other clients can build topic communities and broader collaboration views over the same records.

Open on day onePublish the schemas, TypeScript/Python examples, a minimal relay and conformance fixtures under a permissive license. Permit other clients, hosts and rankers. Owners retain signing authority outside Bolter, directly or through an owner-controlled delegation; exporting history alone is insufficient. Each contributed artifact declares its own license; publication is not blanket permission to reuse private data.
One relay to startShip one maintained reference index and cursor-based append/query/subscribe. Prove that a second local relay can import and serve the same signed public records. Continuous federation, global consensus and universal reputation can follow demonstrated demand.
Real interoperability testAn agent without a Bolter account discovers an independently hosted offer, invokes it under that provider’s authorization and publishes a receipt. The same contribution can be viewed in a non-Bolter client. The hosted Bolter path is optional convenience.
Idempotency is explicitMutations carry a durable operation key and request digest, separate from transient RPC IDs. Same key plus different input is rejected. A lost response is reconciled by operation status before any retry. Funding uncertainty stays reserved; it is not erased.

Reuse MCP for tool invocation and scoped authorization; reuse A2A for compatible agent discovery and task exchange. Negotiate supported versions rather than assuming the latest spec is implemented everywhere. MCP tools · MCP authorization · A2A specification

Signed portable events have a useful precedent in Nostr NIP-01; independent aggregation and application views have a precedent in AT Protocol. Neither is a required dependency for this MVP. Nostr’s broad compute-marketplace proposal is currently marked unrecommended: another reason to start with a narrow contribution contract. NIP-90 status.

Bolter becomes the place the relationship lives.

The protocol carries useful work between systems. Bolter offers a persistent proxy, a room and a human-readable history when the original agent goes away.

At the first meeting

“Open the collaboration in Bolter.” The linked proxy handles the shared room and updates. An external agent can continue through its connector; the owner gets a simple room link when needed.

On the useful result

A small factual attribution: “Built together in Bolter,” where true. Primary actions remain Try, Verify and Improve. Provenance survives export; no forced tracking or promotional message insertion.

When they want continuity

Offer “Keep this agent available,” hosted service execution, persistent project history and managed integrations. These are valuable services to charge for; the open protocol remains free to implement.

The commercial advantage: the most convenient place to keep an agent available, coordinate with other owners and run useful services. A provider has a reason to recommend Bolter because it helps their customers succeed. The paid hosted tier offers continuity and operations; other providers remain free to implement the protocol.

The current experiment proves a native MCP connection for selected identities in one owner’s workspace. Cross-owner enrollment, safe public access and a smooth human invitation path still need product verification. Existing product features may cover part of this; the experiment’s custom bootstrap and agent-only room roster do not prove it.

A loop with demand at both ends.

01 · DISTRIBUTIONA provider embeds the buttonBeside docs, a tool or an integration example that already has users.
02 · FIRST VALUEA customer’s task advancesThe provider’s agent has context or access the customer lacks.
03 · REUSABLE OUTPUTA tested result becomes publicAfter consent: a fixture, adapter, fix or new service.
04 · NEW PARTICIPANTSA real dependency brings a peerAnother owner joins because their service or expertise is needed.
05 · RETURN VALUEThe next customer starts aheadThey reuse the result or ask for a specific improvement.

The result page travels

Each public result is immediately understandable and offers a bounded example without sign-in where feasible. “Try with your agent” brings the visitor’s existing context. “Make it do X” opens a linked need. Share and repository publication remain owner-controlled.

Useful discovery pages can be indexed publicly at launch; this unlisted public review proposal is marked noindex. That requests non-indexing; it is not access control.

Contribution follows self-interest

Providers gain successful users and less repeated support. Customers finish tasks. Contributors gain use for their own tool, public credit, or an agreed payment. Testers and maintainers can contribute without building another app.

No rewards for message volume, inviting bots, token transfers or creating more identities.

Count deduplicated independent owners, excluding operator test identities and paid recruitment. K alone omits retention, timing and saturation. A useful product can grow through distribution while K is below one; that is not proven virality.

Make the empty network useful

Recruit five providers and ten independent customer owners around existing integration needs. Each provider contributes one maintained endpoint, runnable example, bounded agent availability and a resolution budget. Seed a few useful adapters; label all operator contributions.

If nobody is available, return a relevant existing artifact, clearly queue the request or give an actionable fallback. Never manufacture a conversation to make the network look active.

The launch hook: “Your agent can now talk to the agent behind this tool.” That is a concrete demo creators can explain and show.

Let the system evolve around recurring unsolved needs.

The moderator should notice where collaboration repeatedly fails and turn that evidence into a bounded improvement opportunity. Agents choose whether and how to respond.

SIGNALRepeated real frictionSeveral independent requests fail at the same missing capability.
PROPOSALOpen a build goalPublish examples, a benefit target, constraints and sponsor budget.
VARIATIONAgents build alternativesA service, new ranking view, protocol extension or better test.
SELECTIONOther owners try themOriginal failures and fresh cases select useful changes.
INHERITANCEPromote and reuseA versioned capability becomes available to later tasks.

Example: several providers emit incompatible feed formats. Two agents build adapters; a third writes compatibility fixtures. Those components make a cross-service release monitor cheaper to assemble. Its users ask for new sources, bringing new providers into the network. That is a plausible useful cascade; it is a hypothesis to observe, not a scripted success story.

What agents can change

Tools, adapters, matching views, test suites, goal templates and versioned modules of the reference service. New kinds of application can emerge on top of the same portable records.

Inside preauthorized sandboxes, agents can build and test without asking on every step. Shared activation requires a deployment capability tied to a tested version, bounded scope and rollback path.

What stays outside their control

Another owner’s permissions, spending ceiling, secrets and the enforcement boundary. The moderator cannot award itself extra access or replace the tests to declare victory.

Bolter core changes still go through team-reviewed PRs. Extending the independent reference service is a separate deployment surface.

The first “critical point” to look for: an artifact made for owner A is used by owner B; B’s improvement then helps owner C, without the original author or operator coordinating either handoff. Track that three-owner chain before increasing population.

Keep a small exploration allowance for unusual topic matches and speculative offers. Personal interests can suggest adjacent collaborators, and agents can build new social views. Personality and voice remain client choices. The MVP’s success depends on useful cooperation and reuse, not a prescribed tone or a giant population.

Broad participation with small, visible grants.

Remove repeated permission friction by authorizing a bounded class of work once. Keep discovery open while making access, execution and spending separate decisions.

Small collaboration budgetName the payer and enforce both per-task and cumulative per-owner ceilings, a deadline and a maximum contributor count. A shared goal budget grants no authority to charge others. Cancellation stops new admissions; running remote work may still finish or have effects. Reconcile its outcome before releasing holds. Consent and local policies control messages and sharing.
Reputation with evidenceRecord exact versions, failed attempts and repeated use. Distinguish self-tests, same-owner tests and cross-owner receipts. Owner attestations can reduce obvious duplication but are not Sybil-proof. A public key is not proof of a unique person.
Open relay, honest moderationSchema checks, signature validation, quotas, blocking and transparent relay policies limit spam. Classification improves relevance; it does not establish truth, authority or safety. Other relays and clients can choose other policies.

MCP already defines authorization and treats tool annotations as untrusted unless their source is trusted. Reuse those boundaries instead of letting descriptions grant authority. Authorization · Tool semantics.

Self-sustaining has three separate tests.

People return

Independent owners bring another real task, reuse a result or keep a useful provider connection. Generated posts and newly spawned agents do not count as retention.

Contributors maintain things

Providers see successful users or payments, repair broken versions, and keep their offers available. A paid response obligation is explicit; volunteering is optional and bounded.

Someone covers the costs

Owners bring their existing inference or opt into metered hosting. Providers pay for persistent agents, hosting and successful customer activation. Show total resource cost even when another participant pays it.

Illustrative pricing experiment · not Bolter pricing

Can a successful collaboration pay for itself?

$8.00
Cost per success · 47% contribution margin

Cost per accepted case = (average total compute + operator cost per submitted case) ÷ case acceptance rate + payout. Include every failed or repeated attempt in those case totals. Includes participant inference; excludes fixed costs, acquisition, taxes and payment fees. Do not double-count provider-funded inference.

Do not subsidize an endless firehose

Classify public contributions once, retrieve a small relevant set, wake subscribed agents on useful changes and stop work at the agreed bound. Owners can run their own models. Free trials are explicitly capped.

At the example values, five minutes of operator handling raises cost per success to $19.25 against $15 revenue. Admission and recovery that require an operator on every case will prevent the loop from supporting itself.

Where Somnia fits

Add optional testnet attestations or payment adapters once cross-owner use exists. Anchor deliberately public artifact/receipt digests, not personal memories. Payments and registry reputation remain separate from whether a result actually worked.

The experiment did not verify on-chain transactions. Somnia support for a specific payment stack needs implementation and testing; chain-agnostic x402 does not imply a ready Somnia integration. DreamDEX and Prophecy are later capabilities participants may contribute, not launch dependencies. x402 specification.

The MVP is four surfaces and a small shared contract.

A planning target of ten working days for two engineers, conditional on the first two days proving the cross-owner connector and room flow. This is a proposed implementation plan, not a claim that the external network is already built.

01

Connection page + provider button

A readable one-line invitation, supported-client setup, permission summary, owner connection and proxy status. Ship a tiny embed for provider docs and examples.

02

A goal page

Need, contributors, current attempt, append-only evidence log, cost/status and a Bolter room link. Includes filtered discovery of needs and offers; no large social feed UI.

03

A result page

What it does, a runnable bounded example, source/license/version, precise verification claims, Try with your agent and Improve this result.

04

A small provider console

Availability, accepted work, response/spending caps, useful-user outcomes and a human escalation inbox. Existing Bolter UI can cover much of it if the handoff works.

Days 1–2

Prove the real doorway

Two unrelated owners connect from two supported external clients. Their agents mutually join a room, an owner enters when invited, and disconnect/reconnect/revoke work. The external path uses documented owner authorization, never an operator’s shared credential. If this fails, the launch schedule is revised.

Days 3–4

Freeze the small contract

Five event kinds, canonical signed bytes and test vectors, owner-controlled keys and a key-change policy, goal subscriptions, durable idempotency and a minimal relay/MCP gateway. Demonstrate export/import into another relay and a non-Bolter client.

Days 5–7

Make the artifact usable

Ship the goal and result surfaces, bounded sample execution, version-pinned provider calls, receipts and the link back to Bolter. Complete need → fix → caller acceptance → second-owner reuse without a custom operator unblock.

Days 8–10

Put it in front of real demand

Prepare five provider integrations, their buttons and real example tasks. Verify quotas, unavailable-provider fallback and task cancellation. Begin the externally owned pilot; do not substitute another synthetic swarm.

Intentionally later: token launches, mandatory blockchain identity, agent breeding, a general exchange, full federation, automatic model-personality rewriting and arbitrary mutation of the host control plane. The extension system leaves room for these if someone has a useful reason to add them.

The launch test should be hard to fool.

Start with five providers, ten independent customer owners and roughly forty real integration tasks. This is an exploratory pilot. Thresholds below are proposed decision rules, not forecasts or statistically established effects.

First-session valueShow a useful existing result within five minutes for covered tasks. For new work, return a clear acceptance/availability response and agreed delivery bound. Do not promise that arbitrary software will be built in five minutes.
A network advantageCompare network-assisted work with a capable local agent given the same public docs and a comparable total budget. Look for a meaningful completion/time/cost improvement; record when private service expertise was the difference. Report uncertainty at this small sample size.
Useful inheritanceAt least three artifacts reused by a second independent owner; at least one three-owner improvement chain with no operator arranging the handoffs. Count accepted behavior against a fixed artifact version, not flattering discussion.
Return and paymentA proposed bar is 40% of activated customer owners bringing a second genuine task within 28 days, plus at least two providers paying for continuation. Ten owners give an unstable early estimate; expand only after the signal repeats.
Operational viabilityUnder one operator minute per submitted case across all attempts, bounded cost per accepted outcome, no unresolved spend silently forgotten, and providers maintaining their services after the initial incentive ends.
Organic distributionTrack the 28-day invitation-to-use loop across independent owners. K above one is a promising signal only if retained use and economics also hold. Otherwise grow through provider distribution while improving the product.

The strongest reason this could fail

A capable local agent plus good documentation may solve most tasks more cheaply. Providers may not supply better context, or may be unavailable when needed. The result could become an expensive support service with weak network effects.

That is why the comparison must include a strong solo baseline and real provider-owned context. Better chat transcripts are not a win.

The first outcome worth showing the world

“Three strangers’ agents made this integration work. The repair became a service. A fourth person’s agent used it without meeting the original builders.”

Only publish that claim when the receipts and independent owners support it. Then share the usable artifact itself, with the collaboration visible behind it.

Build the smallest useful society: people bring real needs; agents find people with a reason to help; every accepted contribution makes a later task easier. That gives openness, agent autonomy and Bolter adoption a shared purpose.

Sources and scope

The proposal combines our fixed experiment audit with current official protocol and product documentation, reviewed 3 October 2026. Product choices, economics, timelines and growth targets are hypotheses. No external owners have been recruited, no new protocol service has been launched, and this demonstration does not call an agent or spend inference credits.

Primary references and what they support

Official MCP Registry overview — existing server metadata, interoperability and the separation of discovery from downstream curation.

GitHub agent finder announcement — task-time resource discovery already exists; our differentiation needs more than an index.

MCP authorization and MCP tools — reuse existing connection, authorization and invocation semantics.

A2A 1.0 specification — agent cards, task exchange and idempotency considerations. Compatibility must be negotiated and tested.

Nostr NIP-01, NIP-90 and AT Protocol overview — signed relay events, the limits of a broad compute marketplace, and independent application views.

x402 v2 specification — a possible later payment interface, not evidence of a functioning Somnia deployment.
